# WealthOS Mobile — Offline Strategy & Synchronization Engine

> **Document Version:** 2.0.0  
> **Subsystem:** `apps/mobile/src/storage.ts` (`OfflineSyncQueue`)  
> **Status:** Active & Implemented  

---

## 1. Bounded Offline Philosophy

In enterprise wealth management, unconstrained offline mutations present severe data integrity and fraud hazards. WealthOS Mobile enforces a **bounded offline strategy**:
1. **Cached Read-Only Visibility:**
   When offline or during network dropouts, the mobile application permits browsing previously cached account balances, portfolio holdings, budget envelopes, and strategic goals.
2. **Explicit Connection State:**
   The application displays real-time synchronization badges (`SYNCED`, `RECONCILED`, `OFFLINE`). Cached data carries timestamps indicating data freshness.
3. **No Silent Ledger Confirmation:**
   Offline financial operations are **never** presented as confirmed double-entry ledger entries until the backend PostgreSQL server responds with an HTTP 201 Created and an immutable journal entry ID.

## 2. Offline Mutation Queue State Machine

Implemented in `apps/mobile/src/storage.ts` via `OfflineSyncQueue`:

```
          ┌───────────────────────────┐
          │          QUEUED           │
          │  (Action enqueued with    │
          │   tamper-proof checksum)  │
          └─────────────┬─────────────┘
                        │ startSyncing()
                        ▼
          ┌───────────────────────────┐
          │          SYNCING          │
          │ (Payload integrity checked│
          │   prior to dispatch)      │
          └──────┬─────────────┬──────┘
                 │             │
  markCommitted()│             │ markFailed()
                 ▼             ▼
  ┌─────────────────────────┐  ┌─────────────────────────┐
  │        COMMITTED        │  │    FAILED_RETRYABLE     │
  │ (Confirmed by PostgreSQL│  │   (Retry count < 3)     │
  │    journal entry ID)    │  └────────────┬────────────┘
  └─────────────────────────┘               │
                                            │ retryCount >= 3 or
                                            │ Tamper Detected
                                            ▼
                               ┌─────────────────────────┐
                               │      FAILED_FATAL       │
                               │(Quarantined for review) │
                               └─────────────────────────┘
```

## 3. Cryptographic Tamper-Detection Checksums

Before any offline mutation is transitioned to `SYNCING`, `OfflineSyncQueue` recomputes the payload checksum:
```typescript
export function computeMutationChecksum(action: string, payload: Record<string, unknown>): string {
  const str = `${action}:${JSON.stringify(payload)}`;
  let hash = 0;
  for (let i = 0; i < str.length; i++) {
    hash = (hash << 5) - hash + str.charCodeAt(i);
    hash |= 0;
  }
  return `chk-${Math.abs(hash).toString(16).padStart(8, '0')}`;
}
```
- If local storage was manipulated, tampered with, or corrupted while queued, `mut.checksum !== currentChecksum`.
- The mutation is immediately transitioned to `FAILED_FATAL`, quarantined, and rejected with:
  `"Tampering detected in mutation: checksum mismatch"`.

## 4. Conflict Resolution & Idempotency

- Every financial mutation request generated by the mobile client includes a unique client-side `idempotency_key` (e.g. `tx-173116...`).
- If network connectivity drops after the server processes the request but before the client receives the response, retrying with the same idempotency key ensures the backend does not post a duplicate journal entry.
- Exponential backoff (1s, 2s, 4s) governs retry attempts for transient network failures.
